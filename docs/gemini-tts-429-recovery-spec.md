# Gemini TTS 整本書限流恢復規格

日期：2026-11-05。狀態：CLOSED（2026-11-13整理，實作交付已於11-05完成）。[交付證據](verification/gemini-tts-429/README.md)記錄33項通過、原生及正式封裝結果。未做真實長書服務壓測；下文為保留的策略與驗收契約，不再排入待實作。

## 1. 目標與範圍

讓 Gemini TTS 在製作長篇／整本書音訊時，遇到暫時 HTTP 429 後自動等待並繼續目前區塊，不因連續三次限流就中斷整個製作任務。已成功區塊保留並重用；等待中可取消。

本次修改 Gemini TTS 的限流分類、排程、重試及現有進度顯示。沿用逐塊合成、音訊快取、批次 MP3／SRT、總音訊與影片流程；不新增跨批次全書排程器，不自動更換模型、服務或金鑰。Fish Audio、Edge TTS、Kokoro 保持既有策略。

本文件中的數值是本產品的實作預設，不是 Google 公布的配額或恢復保證。帳戶每日配額或帳務限制仍可能需要使用者介入；本次不實作跨日常駐自動續作。

## 2. 使用者補充與官方依據

使用者指出：每日配額用盡可能從服務回應辨識，例如要求等待到接近一天後。實作必須使用回應中的原因與等待提示，不能把所有 429 都當成短期限流。

判斷原則：

- 明確的每日配額欄位或錯誤原因，可判定為每日配額用盡。
- 數小時至近一天的等待時間，足以判斷本次不適合短期自動重試，但秒數本身不能證明是每日配額。
- 每日配額若接近重設時間，也可能只剩短等待。因此明確的配額原因優先於等待長短。
- 回應缺少原因或時間時，保留「原因未明」分類，不推測帳戶方案或恢復時間。

已查核的 Google 官方文件：

1. [Rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)：RPM、TPM、RPD 等限制分別評估；配額按 Google 專案而非 API Key 計算；RPD 在太平洋時間午夜重設。實際模型限制應查 AI Studio。未確認 RPM 一律採特定滾動視窗演算法，不能假設 60 秒內必定恢復。
2. [Troubleshooting／Retry strategy](https://ai.google.dev/gemini-api/docs/troubleshooting)：暫時性錯誤採指數退避、jitter 與有限重試。

實作者若依賴特定端點的 JSON 錯誤欄位，須查核該端點現行文件或去識別化回應。支援常見的 `google.rpc.RetryInfo`、`google.rpc.QuotaFailure` 時，視為可選資訊，不假設每次都會提供。

## 4. 回應解析與分類

以結構化資料傳遞分類及時間，不以中文顯示文字包含某詞作為控制流程。可擴充現有例外或建立小型結果物件，至少承載：HTTP status、分類、服務等待秒數（可缺省）、時間來源、安全摘要。

### 4.1 分類順序

| 分類 | 可接受證據 | 行為 |
| --- | --- | --- |
| 帳務／永久限制 | 明確的 billing、餘額不足、帳戶停用或零可用配額資訊 | 停止自動重試，保存進度，提示處理帳戶 |
| 每日／期間配額用盡 | quota metric／quota ID 明確含 daily、per_day、PerDay 等日限制語意，或明確期間配額錯誤 | 停止自動重試，保存進度，顯示服務指定時間（若有） |
| 暫時限流 | 明確的 RPM、TPM、PerMinute、並行限制或 rate limit 原因 | 進入自動等待 |
| 原因未明的 429 | 僅有 RESOURCE_EXHAUSTED、泛稱 quota exceeded、空白或無法解析的回覆 | 有限自動等待；長等待依第 5 節停止 |

`quota_exceeded`、RESOURCE_EXHAUSTED、HTTP 429 本身不代表每日配額。若同時出現短期與長期限制，採明確需要介入的限制。不能把錯誤訊息內一般文件連結或說明文字誤認為實際 quota metric。

### 4.2 等待提示

- 支援 Retry-After 的數字秒數與 HTTP-date。
- 支援已確認結構內的 RetryInfo.retryDelay，例如 `12.5s`；其他端點格式先確認再加入。
- 若有多個有效等待提示，取最晚允許重送的時間；不得截短服務指定時間以符合本機上限。
- 排除非有限數、負數、畸形值；過去時間視為已到期，但仍套用本機退避以免忙迴圈。
- 只解析有限大小的錯誤本文，維持現有 64 KiB 保護。回覆過大或非 JSON 時安全退回原因未明。
- 不把 API Key、完整書稿、Authorization header 或原始錯誤本文寫入進度、SQLite、畫面及測試證據。

## 5. Gemini 暫時 429 的恢復策略

只對 Gemini 的暫時／原因未明 429 套用本節。一般網路錯誤、timeout、5xx 與其他服務維持原策略，避免將所有失敗都延長為長等待。

### 5.1 自動等待預設

- 第 n 次連續 429 的本機退避：`min(60, 5 * 2**(n-1))` 秒，再加 0～5 秒均勻 jitter。將亂數與時間來源設計成可測試。
- 實際等待至少為「本機退避、服務指定剩餘等待、共用冷卻剩餘等待」三者最大值。
- Gemini 429 不消耗原有一般錯誤三次上限；使用獨立計數與預算。普通錯誤仍須有限次重試，混合錯誤不能繞過各自上限。
- 同一未完成區塊最多容許 30 次實際 429 回覆。第 30 次仍為 429 即停止，不發第 31 次。
- 從該區塊第一次 429 起，最多自動恢復 1,800 秒。以單調時鐘計算連續無進展的實際經過時間，包含等待、排隊與重試請求時間。
- 若下一次合法重送時間將超過 1,800 秒期限，立即保存並停止；不先空等剩餘預算。恰在期限時不再發出請求。
- 每次重試請求仍有原本的單次 timeout，且不得超過恢復期限的剩餘時間。等待須放在單次網路 timeout 外，避免 90 秒 timeout 把長冷卻截斷。
- 成功取得並驗證目前區塊後，下一區塊重設上述 429 次數與無進展預算。整本書不共用一個累積 30 分鐘上限。

例：服務要求 77,813 秒 → 第一次回應後保存並停止 → 顯示約 21 小時 37 分後可再嘗試，不進入長休眠。沒有明確日配額原因時，文字為「服務要求長時間冷卻」，不是「每日配額已用盡」。

### 5.2 主動限速與共用冷卻

- 保留 `tts-limits.json` 現有 provider:model 的 requests_per_minute 設定與驗證，相容舊檔。
- 未明確設定時，Gemini 採本產品保守預設 5 RPM，即至少 12 秒請求起始間距；其他 provider 預設不變。文件明示這不是帳戶保證值，使用者可按實際配額設定。
- 每次 Gemini 429 將該 scope 的有效間距加倍，上限 `max(60 秒, 設定間距)`。成功後不立即加速；最後一次 429 過 10 分鐘後才恢復設定間距。持久化必要資訊，使重開程式不立即恢復突發請求。
- 同 scope 的試聽、製作與多個本機程序共用冷卻及間距。等待結束後重新檢查冷卻並取得合法發送時段，避免所有等待者同時送出。
- 對可恢復的短期冷卻，`before_request` 應等待或回報可等待的結構化結果；不能拋出一般不可重試錯誤結束任務。已知配額／帳務限制仍走停止路徑。
- SQLite 交易內不 sleep、不持有跨網路請求的鎖。取消保留服務冷卻，但釋放本次排程資源；其他工作仍可使用資料庫。
- 現有 scope 是金鑰＋模型，不等同 Google project。此次不新增 Cloud project 探索或 UI 欄位；清楚記錄不同金鑰、其他電腦與外部程式仍可能共用 Google 配額。避免宣稱已完成 Google 專案級限流。

## 6. 狀態、續作與操作

沿用現有等待倒數、取消按鈕、狀態摘要及詳情區，不新增版面。若實作者確實需要新增或調整版面，先提供設計圖並取得使用者確認，再實作該版面。

- 短期等待：任務維持執行中，目前區塊為等待／執行中；失敗數不增加。範例：「Gemini 暫時限流，58 秒後重試 · 區塊 43/173」。
- 倒數由目前截止時間計算。其他請求延長冷卻後同步更新，不顯示負數或停在原秒數。
- 詳情提供 HTTP 狀態、分類、重試次數、等待依據及停止原因。由產品規則推定的時間須標示「本機退避」；由服務回傳的時間標示「服務指定」。
- 停止：明確區分「每日配額」、「帳務」、「服務要求長時間冷卻」、「連續限流超過恢復上限」。服務指定的時刻以本機時間顯示，標示為最早可再嘗試時間，不保證屆時一定成功。
- 等待中按取消，應在 3 秒內完成本機取消並釋放工作資源。取消後不再發出新請求；已在遠端處理的請求不宣稱已被服務撤銷。
- 停止、取消或關閉後保留驗證成功的音訊與進度。續作只傳送尚未完成／快取失效的區塊；舊失敗列及摘要須同步更新。
- 服務冷卻跨重啟保留。重啟後由使用者啟動續作，不自動傳送書稿。續作前仍檢查文字傳送同意；取消勾選時不得發送。
- 舊版進度檔及 SQLite 必須相容或無損遷移，不能丟棄仍有效的冷卻。無法辨識的舊冷卻原因採保守處理。

## 7. 驗證要求

採可控時鐘、合成金鑰與本機假 HTTP 回覆。不得實際等數十分鐘或大量消耗帳戶配額來驗證限流。至少一組整合案例須走真實 `request_audio → tts_control → speech_block → NarrationJob` 路徑，不能替換掉 before_request／record_limit 後就宣稱共用冷卻通過。

| 案例 | 可觀察結果 |
| --- | --- |
| 第 36 塊連續 4 次暫時 429，第 5 次成功 | 同一次任務自動完成；前 35 塊各自只合成一次；輸出可解碼 |
| 多個後續區塊各自遭遇 429 後恢復 | 每塊預算獨立，整本書不因累計等待超過 30 分鐘停止 |
| 無 Retry-After 的短期 429 | 等待符合 5、10、20、40、60 秒基底與 jitter；沒有忙迴圈 |
| Retry-After 120 秒；RetryInfo 150 秒 | 最早 150 秒後重送；不被單次 90 秒 timeout 中斷 |
| HTTP-date、過去時間、負值、NaN、Infinity、畸形 JSON、過大回覆 | 安全解析／退回；沒有例外洩漏或零等待重送迴圈 |
| 泛稱 quota_exceeded，沒有日配額證據 | 不誤判為每日配額 |
| 明確 PerDay，等待只剩 20 秒 | 依每日配額分類停止，不當成 RPM |
| 原因未明，要求 77,813 秒 | 一次請求後停止；顯示長冷卻；保存指定時間與進度 |
| 持續短期 429 | 達次數或時間上限後停止；以先達者為準；不超額重送 |
| 429 與 timeout／5xx 混合 | 各自重試限制有效；無限重試不可發生 |
| 同 scope 多工作／至少兩個程序同時等待 | 冷卻共享；恢復後仍有間距；SQLite 不長時間鎖住 |
| 等待中其他工作延長冷卻 | 延後重送並更新倒數；任務不因一般 ProjectError 中止 |
| 自訂 RPM、預設 RPM、429 後降速與 10 分鐘後恢復 | 發送時間符合策略；重啟仍保留有效保護 |
| 等待中取消、關閉程式 | 3 秒內本機取消；無後續請求、殘留鎖、暫存與自有程序 |
| 取消後重開專案並續作 | 重用成功區塊；遵守尚未到期冷卻；未勾同意時零請求 |
| 舊 SQLite／進度檔 | 可開啟、續作；有效冷卻及已完成區塊不遺失 |
| Fish Audio、Edge TTS、Kokoro 回歸 | 原有重試、timeout、快取、取消及合成功能維持 |

原生 UI 驗收路徑使用短句：

1. 開啟專案 → 按「試聽與製作」→ 按「製作與成品」。
2. 啟動測試製作 → 觸發暫時 429 → 確認倒數持續變動。
3. 等待假服務恢復 → 確認原任務繼續 → 確認已完成數增加。
4. 再次觸發等待 → 按「取消任務」→ 確認 3 秒內顯示已取消。
5. 重開專案 → 按「繼續未完成區塊」→ 確認成功區塊被重用。
6. 觸發長時間冷卻 → 確認工作停止 → 確認原因與最早重試時間可見。
7. 還原及縮小視窗 → 確認狀態文字、主要操作與取消按鈕未裁切。

實作者應按實際 UI 核對操作名稱。真實服務測試若執行，只做少量驗證並保留去識別化證據；模擬測試通過不能描述為已證明真實整本書零中斷。

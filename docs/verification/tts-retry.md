# 製作與成品：長等待要求與續作

2026-10-31。

後續修正：對超長等待加入每區塊 300 秒自動等待總額，並同步續作清單及倒數。請使用 [超長服務等待修正版](tts-cooldown.md) 所列新版；以下保留第一次修正的驗證紀錄。

## 原因與修正

舊版收到 TTS HTTP 429 或 5xx，且 `Retry-After` 大於 60 秒時，立即拋出「服務要求等待超過60秒，請稍後重試」。這是服務要求下次請求前的等待時間，並非本次已經等待的時間。因此按「繼續未完成區塊」後，即使重新送出請求，也會在收到相同回覆時立即失敗。訊息本身不能區分原始 HTTP 429 與 5xx。

修正 `tts_services.py`，讓大於 60 秒的有效等待要求進入既有可重試流程。`voice_media.py` 在每次請求的 90 秒逾時範圍外等待，最多嘗試 3 次；等待可取消。`narration.py` 將等待秒數傳給既有狀態列，不調整版面。用盡重試時保留 HTTP 狀態、限流／服務原因及等待要求。成功音訊快取、原任務快照與成品發布規則不變。

`Retry-After` 語意依據：[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)。秒數與 HTTP 日期均有測試；無效與非有限數值回退到既有短暫重試間隔。

## 重現與驗證

修正前執行 `python -m unittest discover -s tests -p test_tts_retry.py -v`，36 塊情境在續作時得到 `failed != completed`，錯誤為「服務要求等待超過60秒，請稍後重試」。將情境縮成兩塊，仍在 2.709 秒內重現同一錯誤。另以兩種服務的 HTTP 429／503 直接驗證，舊版在 120 秒等待要求時拋出不可重試錯誤。

修正後用 36 塊完整情境驗證：前 35 塊保留；第 36 塊收到 120 秒等待要求後重試成功；沒有重送前 35 塊。120 秒長等待以模擬時鐘驗證，沒有真的等待數分鐘。另外以真實非同步等待驗證取消，3 秒內停止並釋放任務鎖、媒體暫存與區塊暫存；已成功音訊仍可重用。用盡 3 次重試的測試確認只等待兩次，錯誤保留 HTTP 429 與 120 秒要求。

相關 7 個測試模組共 36 案例，加上原生介面 1 案例，合計 **37 案例通過，0 跳過**。這是相關範圍回歸，並非完整專案測試。各模組證據為同目錄 `tts-retry-test_*.txt` 與 `tts-retry-desktop-tests.txt`。型別檢查 `python -m mypy ebook2mp4 --check-untyped-defs` 通過 25 個來源檔案，見 `tts-retry-typecheck.txt`。

原生 Tk 測試以 1040×640 視窗驗證等待時停用開始、啟用取消及控制項邊界，並按取消完成流程。[等待畫面](tts-retry-wait.png) 已目視檢查，狀態文字與按鈕沒有裁切或重疊。此次為 Python／Tk 桌面狀態回報修正，未使用瀏覽器驗證；其他 DPI 未測。

服務回覆使用合成資料及 HTTP 替身。未讀取使用者書稿或金鑰，未向真實 TTS 服務送出請求。實際服務的配額或故障是否恢復，仍依服務端結果決定。

1. 關閉舊版 → 開啟新版 → 開啟原專案。
2. 按「試聽與製作」→ 按「製作與成品」→ 選取原失敗任務。
3. 按「繼續未完成區塊」→ 檢查已完成區塊被重用。
4. 服務要求等待時 → 檢查顯示「等待 N 秒後重試」→ 檢查任務仍在執行。
5. 等待結束 → 檢查未完成區塊再次合成。
6. 按「取消任務」→ 檢查工作停止 → 檢查成功區塊仍可續作。
